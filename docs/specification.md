# Kouga — APIフレームワーク仕様書

状態: 初稿（実装前）  
作成日: 2026-09-25  
対象: 初版の機能・振る舞い・受け入れ条件

T01で具体化した型・依存・生成記法は[共通API契約](api-contracts.md)を参照する（レビュー承認済み・実装前）。本書中の「実装時に確定」「設計案」は、同契約で具体化した項目についてはそちらを優先する。機能範囲・受け入れ条件は本書を維持する。

## 1. 目的

Rustで、規約に沿って少ない記述でAPIアプリケーションを開発できるフレームワークを作る。RailsのAPIモードを参考に、ルーティングから永続化、バックグラウンド処理、運用までを一貫した開発体験として提供する。

本書に挙げた全機能を初版の完成範囲とする。段階的に実装するが、後半の機能も必須とする。RailsとのAPI互換性や内部構造の再現は要求しない。

## 2. 前提と設計方針

- 対象はHTTP/JSON APIとgRPC/Protobuf。同一プロジェクトで両方の入口を併用できる。標準の開始構成はHTTPとする。HTML画面、フロントエンドのビルド、Rails互換のテンプレート機構は対象外。メール本文のテンプレートは対象に含む。
- Rustの型でリクエスト、レスポンス、モデル、ジョブの引数を表現する。
- HTTP入力の検証は専用のRequest型に定義し、controllerの呼び出し前に自動実行する。
- ルート・Request・レスポンスの定義から`openapi.yml`を自動生成する。入力検証とAPIドキュメントで同じ定義を使用する。
- 規約による標準構成を提供し、環境差や実際の用途に必要な設定は変更可能にする。
- HTTP、暗号、DBドライバなどの基盤は既存実装を利用する。新規開発の中心は統合、規約、開発者向けAPIとする。
- 内部エラーや機密情報を外部へ漏らさない。入力検証、認可、データの整合性は省略しない。
- 明示的な処理を基本とし、任意のモデルコールバックや暗黙の関連取得は導入しない。
- HTTPサーバー・gRPCサーバー・workerは別の実行ファイル・Dockerイメージとしてビルド・デプロイできる。model・業務処理・ジョブの引数定義を共有し、各実行ファイルには必要な依存だけを含める。
- 非同期ランタイムにはマルチスレッド版Tokioを採用する（合意済み）。HTTPサーバーをアプリケーションの実行ファイルへ組み込む。

以下は初稿の設計上の提案であり、ユーザーによる指定事項とは区別する。

| 項目 | 初版の標準 |
|---|---|
| DB | PostgreSQL。複数DB製品への対応は初版の対象外 |
| ジョブ・共有キャッシュ・配信通知 | PostgreSQLを利用し、必須インフラをまとめる |
| 認証 | 失効可能な不透明Bearerトークン |
| メール | SMTP、本番以外ではメモリへの記録も可能 |
| ストレージ | ローカルファイルとS3互換オブジェクトストレージ |
| 設定 | 設定ファイルと環境変数。秘密情報は環境変数またはマウントされたファイルから取得 |
| 時刻・識別子 | UTC、JSONの日時はRFC 3339、生成モデルの標準IDはUUID |

## 3. アプリケーション構成

生成アプリケーションは単一リポジトリ内のCargo workspaceを標準とする。HTTP・gRPC・workerの依存を分離し、共通model・業務処理とジョブの契約を共有する。以下は責務の配置であり、gRPC・workerなど未使用のパッケージ・ディレクトリは必要になったときに生成する。

```text
Cargo.toml
crates/
  domain/src/models/
  contracts/src/jobs/
  rpc/src/             # .protoから生成する型。gRPC追加時のみ
apps/
  http/src/
    main.rs
    routes.rs
    controllers/
    requests/
    middleware/
    auth/
    channels/
    config.rs
  grpc/src/
    main.rs
    handlers/
  worker/src/
    main.rs
    jobs/
    mailers/
    config.rs
proto/                # gRPC追加時のみ
migrations/
tests/
Dockerfile
```

ルート確定後の標準経路は、middleware → request validation → controller → model → DB → JSONレスポンスとする。全体middlewareはルート解決の外側、ルート固有middlewareはその内側で実行し、どちらもrequest validationより先に処理する。認証必須ルートでは入力検証より先に認証する。業務処理のための追加レイヤーは必須にしない。

Request型は操作ごとに定義し、入力項目と検証ルールをまとめる。例えばCreateTaskRequestとUpdateTaskRequestを分け、modelの保存時にHTTP入力を検証する構成にはしない。controllerは検証済み入力を受け取って認可と処理を組み立て、modelは永続化とHTTP以外からの呼び出しでも必要な業務上の不変条件を担う。

### 3.1 サーバーの実行モデル

`kouga server`は、選択した入口のサーバーとマルチスレッド版Tokioを起動する。HTTPのみまたはHTTP/gRPC併用の構成ではHTTPが既定となり、gRPCのみならgRPCを起動する。`--api http|grpc`で入口を明示できる。標準は1サーバープロセス内の複数OSスレッドで多数の非同期タスクを実行する構成とする。リクエストごとのOSスレッド作成や、Pumaのような別のアプリケーションサーバーの導入は要求しない。

```text
サーバープロセス
└─ Tokioランタイム
   ├─ 実行スレッド1：タスクA → I/O待ちで実行を譲る → タスクB
   ├─ 実行スレッド2：タスクC → I/O待ちで実行を譲る → タスクD
   └─ 実行スレッドN：実行可能なタスクを処理
```

- Rustには通常のコードの並列実行を制限するRubyのGVLに相当する仕組みはなく、異なるスレッドで処理を並列実行できる。
- middleware → request validation → controller → modelの呼び出し経路を非同期処理に対応させる。DBや外部HTTPの待機中は、スレッドを占有せず別のタスクを進められる実装を使う。
- 各レイヤーで別タスクを生成する必要はない。通常は同じ処理の流れでawaitする。接続・リクエストとタスクの具体的な対応はHTTP実装に委ねる。
- Tokioのタスク実行は協調的であり、asyncを付けるだけで処理が別スレッドへ移るわけではない。await先が即座に完了する場合もあり、awaitの存在だけで他タスクへの実行機会を保証しない。
- パスワードのハッシュ計算などの重い計算や、同期I/Oは`spawn_blocking`などで非同期処理用のスレッドから分離する。投入前に同時実行数を制限し、待機数・待機時間にも上限を設ける。
- 開始済みの`spawn_blocking`処理は要求のタイムアウトだけでは停止しない。実行枠は処理完了まで保持し、切断・タイムアウト・終了時の扱いを明記する。
- リクエスト固有のデータは各処理で所有し、DB poolや設定などを共有する。共有可変状態は同期を伴う型で管理し、同期ロックを保持したままawaitしない。
- Tokioの実行スレッド数、HTTP同時処理数、DB poolの接続数、重い処理の同時実行数は独立して設定する。過負荷時は無制限に処理を蓄積せず、受付を制限するか503を返す。利用者ごとのレート制限は429とする。
- スケールアウトや障害分離のために複数サーバープロセスを起動できる。プロセスの複製・再起動はデプロイ環境の管理機構に任せ、初版では独自のプロセス管理機構を作らない。
- `kouga worker`は永続queueのジョブを処理する別プロセスであり、Tokioの実行スレッドとは区別する。workerもTokioを利用し、ジョブ並列数をランタイムのスレッド数とは独立して制御する。永続ジョブを`tokio::spawn`だけで代替しない。

受け入れ条件: Tokioの実行スレッドを1本に制限した検証環境でも、I/O待機中のリクエストと分離された重い処理が、独立した軽いリクエストの完了を妨げないことを確認する。複数スレッドでの実行、同時処理上限、過負荷応答、タイムアウト後の実行枠保持、graceful shutdownも検証する。

設計の参照資料: [Tokioのタスク実行](https://tokio.rs/tokio/tutorial/spawning)、[タスクとblocking処理](https://docs.rs/tokio/latest/tokio/task/)。

### 3.2 ビルド単位・依存の分離

- HTTPはdomain・contracts・queue投入用crateに依存し、workerの実行処理・SMTP・メールテンプレートには依存しない。メールを即時送信したいアプリだけがHTTP側へmailerを明示的に追加する。
- gRPCはdomain・必要なcontracts・Protobuf生成型・gRPC基盤に依存する。HTTP controllerやOpenAPI UIへ依存せず、HTTP側にもgRPC基盤を必須にしない。HTTPとgRPCの共通業務処理はdomainの通常のRust関数・型として定義できる。
- workerはdomain・contracts・queue実行用crateと、登録したジョブが必要とするmailerなどに依存する。router・controller・OpenAPI UIを必須依存にしない。
- contractsはジョブ名・payloadのバージョン・型付き引数を定義し、実行処理やSMTP・HTTP基盤へ依存しない。queue投入APIは実行handlerの型を要求しない。
- Kouga側もqueue投入・queue実行・mailerのcrate境界を分ける。未使用機能をすべて有効にする既定featureを避け、最終的な依存グラフで分離を確認する。
- Cargoのパッケージ単位でHTTP・gRPC・workerを個別ビルドする。実行時フラグで同じ巨大なバイナリの動作を切り替える方式を標準にしない。
- メール・画像処理などのworkerをさらに分ける場合は、実行パッケージと購読queueを分ける。共通queueから別用途のジョブを取得して未知ジョブとして隔離しない。
- producerとworkerは独立した時期に更新できる。新payloadの投入前に対応workerを配備し、旧payloadの待機・再試行が残る間は旧版の処理も維持する。
- `kouga server`と`kouga worker`は開発用の起動窓口とする。本番イメージはビルド済みの対象バイナリを直接起動し、開発CLIやCargoを要求しない。

### 3.3 軽量Dockerイメージと配備先

実行方式は、queueを監視し続ける「常駐worker」と、指定した処理や件数・時間の条件に達したら終了する「ワンショットタスク」に分ける。ワンショットタスクは1回の起動で複数ジョブをまとめて処理するバッチにも使え、ジョブ1件だけの実行という意味ではない。

配布単位はLinux向けのDocker/OCIコンテナイメージとする。HTTP用とworker用を独立して作成でき、同じアプリのコードから配備先に合わせたイメージを作る。クラウドの自動構築・公開・デプロイCLIは初版の必須機能にはしない。

- 生成するDockerfileはmulti-stage buildを使い、選択した機能に応じて`http`・`grpc`・`worker`を独立した最終targetにする。ビルド対象のパッケージを明示する。クラウド配備表のHTTP向け対応を、ネイティブgRPCへ自動適用しない。
- 最終イメージにはreleaseビルドした実行ファイル、必要な動的ライブラリ・CA証明書・テンプレートなどだけを含める。ソース一式、Rustツールチェーン、ビルドキャッシュ、テスト、未使用の実行ファイルは含めない。
- 軽量な実行用ベースを選び、デバッグ情報を最終バイナリから分離する。scratchや静的リンクは必須にせず、TLS・DNS・採用依存が正しく動くことを優先する。
- 非root・読み取り専用root filesystemで動作できるようにする。一時ファイルは`/tmp`など明示した場所を使用し、秘密情報はイメージへ焼き込まず実行時に注入する。
- 永続データは外部DB・オブジェクトストレージへ置く。ローカルストレージは開発用または永続volumeを明示した配備に限定する。
- HTTPは`0.0.0.0`と環境変数`PORT`で指定するポートを使用する。ログは標準出力・標準エラーへ出し、終了シグナルを受けて猶予時間内に終了する。
- migration・seed・管理操作は別の管理用ビルドtargetに必要な場合だけ含め、HTTP/workerの通常起動から実行しない。SQLコンソールなどの開発ツールは本番イメージへ必須搭載しない。
- イメージサイズの数値は実測前に保証しない。targetごとに圧縮転送サイズ・展開サイズ・バイナリサイズと起動時間を記録し、依存追加による変化を確認する。

| 配備先 | 実行契約・対応範囲 |
|---|---|
| Cloud Run service | HTTPイメージを使用しPORTでlistenする。リクエスト終了後のバックグラウンド処理に依存せず、必要な処理は永続queueへ投入する |
| Cloud Run Jobs | ワンショットタスク（queue処理・管理処理）を使用し、完了時0、失敗時非0で終了する。常駐polling workerをそのまま無期限実行しない |
| ECS service / task | HTTPとworkerを別taskとして配備できる。常駐workerはserviceとして管理し、ワンショットタスクは単発taskで実行できる |
| Lambda container image | Lambda Runtime API対応が必要。HTTPには既存のHTTP adapterを追加した専用targetを用意し、通常コンテナと同じイメージの無変更利用は保証しない |

- Lambda用のadapterは通常のHTTP/worker targetへ含めない。Function URL等のHTTPイベントをKougaのHTTP処理へ接続する構成を例示し、バイナリ本文・ヘッダー・認証・エラーを検証する。adapterの選定は実装時に行う。
- Lambdaでworkerを実行する場合も、イベントを受ける入口と、処理後に終了するワンショットタスクが必要となる。常駐DB pollingは使わず、外部からの明示的な呼び出しで件数・時間を制限して処理する。PostgreSQL queueが自動的にLambdaを起動するとは扱わない。
- ワンショットタスクは最大件数・実行時間・空queueでの終了を指定でき、終了期限前に新規取得を止める。再試行可能なジョブ失敗はDBへ記録し、基盤障害や処理中の期限超過は非0終了とする。Lambdaの入口は結果をinvocationの成功/失敗へ変換する。
- Lambda上で既存の長時間WebSocket接続や呼び出し終了後の処理継続は保証しない。全配備先で同じ機能が無条件に動くとせず、対応する実行モードを文書化する。
- 自動スケール時の総DB接続数を考慮し、各プロセスのpool上限と最大インスタンス数を設定する。クラウドごとのCPUアーキテクチャ・起動・終了期限に合わせてビルドと設定を選ぶ。

受け入れ条件: HTTPとworkerを別々にビルド・起動し、ジョブ投入からメール送信まで連携できる。HTTPの依存にSMTP・worker handlerがなく、workerにHTTPルートやUIがないことを確認する。両イメージはツールチェーンなし、非root、読み取り専用rootで動作する。PORT・終了シグナル・ワンショットタスクの終了を検証し、各配備先の手順とLambda adapterの結合検証を用意する。実クラウドで未検証の項目は未検証として記録する。

参照: [Cloud Runのコンテナ実行契約](https://docs.cloud.google.com/run/docs/container-contract)、[Lambdaコンテナ要件](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html)、[ECS task定義](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definitions.html)。

## 4. 機能仕様

### 4.1 Router

- HTTPメソッドとパスからcontrollerのactionへルーティングする。
- パスパラメータ、クエリパラメータ、名前空間、ネストしたルートに対応する。
- RESTリソースのindex/show/create/update/destroyをまとめて登録でき、必要なactionのみ選べる。
- 静的パスを動的パスより優先する。同一メソッドで曖昧な定義や重複した定義は起動時エラーにする。
- 未登録パスは404、対応しないメソッドは405とし、405ではAllowヘッダーを返す。
- HEADはGETに準じてヘッダーのみ返す。OPTIONSとCORS preflightを処理できる。
- 登録済みルートをCLIで一覧表示する。

受け入れ条件: RESTルートと独自ルートを混在させ、パス抽出、優先順位、404/405、HEAD/OPTIONSをリクエストテストで検証できる。

### 4.2 Middleware

- アプリ全体とルートグループ単位に適用でき、登録順を実行順とする。レスポンス処理は逆順とする。
- 標準でrequest ID、アクセスログ、エラー変換、タイムアウト、リクエストサイズ制限、CORSを提供する。
- エラー・タイムアウトもrequest ID付きで記録する。認証エラーを含むレスポンスに必要なCORSヘッダーを付与する。
- CORSの許可元を設定でき、未設定時はクロスオリジン許可ヘッダーを出さない。資格情報付きの全許可は認めない。
- 信頼するプロキシを設定でき、未指定の送信元からの転送ヘッダーを信用しない。
- IPまたは認証主体ごとのレート制限を提供する。標準の共有ストアを使い、超過時は429とRetry-Afterを返す。
- 独自middlewareを追加できる。

受け入れ条件: 実行順、途中終了、例外時の記録、サイズ超過、タイムアウト、複数サーバーでのレート制限を検証できる。

#### 4.2.1 独自middlewareの作成・登録

基本案は、`async fn(request, next) -> Result<Response, Error>`という通常の非同期関数を登録する方式とする。独自クラス、継承、専用traitの手書き実装を必須にしない。以下の型名・記法は公開APIの設計例であり、コンパイル可能な実装ではない。

```rust,ignore
async fn require_auth(mut request: HttpRequest<AppState>, next: Next<AppState>) -> Result<Response, Error> {
    let token = bearer_token(request.headers())?;
    let user = authenticate(request.state().db(), token).await?;
    request.extensions_mut().insert(CurrentUser::from(user));
    next.run(request).await
}

// 同じ登録が実行時の認証とOpenAPIのsecurity指定を担う。
router.group("/projects")
    .middleware(bearer_auth(require_auth))
    .resource(projects_controller);
```

- requestはHTTPヘッダー・アプリ状態・型付きextensionsへアクセスできる。検証用のRequest型とは別物として、公開API上も名前を区別する。
- `next.run(request)`で後続へ進み、その戻り値を加工して返せる。Nextは消費して使う型にし、同じ後続処理を二度実行できないようにする。呼び出さずにレスポンスまたはエラーを返すことで途中終了できる。
- 認証主体などのリクエスト固有情報はextensionsへ型付きで格納し、controllerやカスタム検証で読み取る。グローバル変数や文字列キーの共有mapは使わない。
- middlewareは全体→外側グループ→内側グループ→ルートの順で適用し、各階層内では登録順とする。ルートで認証を黙って解除できないよう、公開APIは認証グループの外に登録する。
- request ID・アクセスログ・共通エラー変換・CORSの外側の処理系は、独自middlewareのエラーも扱う。CORS preflightは業務ルートの認証より先に処理する。
- bodyは一度だけ消費するストリームとして扱う。標準authはbodyを読まない。bodyを必要とする独自middlewareはサイズ制限を守り、後続で必要なら明示的に復元する。
- レスポンスヘッダーの加工は本文全体の読み込みを要求しない。ストリーミング応答とWebSocket upgradeを壊さない。
- 任意のmiddlewareから認証仕様を推測しない。上例の`bearer_auth`のような登録ヘルパーは、実行関数とOpenAPIメタデータを一緒に保持する。独自のエラーステータスは登録時に補足できる。
- 標準authは生成コードを使えばよく、独自関数を書くのは認証方式や追加処理を変える場合とする。

authはトークンの欠落・不正・期限切れ・失効を401とし、WWW-Authenticateを付ける。認証ストアの障害を401に置き換えず503にする。対象リソースの認可はcontrollerで対象を取得する際に行い、middlewareで全リソースを先読みしない。

追加の受け入れ条件: 独自関数一つで登録でき、前後処理・途中終了・型付きユーザー情報の受け渡しを検証できる。認証拒否ではvalidationとcontrollerが呼ばれず、DB障害は503になる。認証登録の変更がOpenAPIへ反映される。

### 4.3 Auth：認証・認可

- ユーザーモデルと登録・ログイン・ログアウト・現在ユーザー取得のAPIを生成できる。公開するルートはアプリ側で選択する。
- パスワードは専用のパスワードハッシュ実装を利用し、平文で保存・記録しない。
- Bearerトークンに有効期限を設け、DBにはハッシュのみを保存する。ログアウトとパスワード変更・リセットで対象トークンを失効できる。
- 認証必須ルートと公開ルートを明示できる。未認証・期限切れ・失効済みは401を返す。
- メールによるパスワードリセットを提供する。リセットトークンは期限付き・一度限りとし、保存時はハッシュ化する。
- ログイン失敗とリセット申請では、アカウントの存在を応答内容から判別できないようにする。試行回数を制限する。
- 認可は「主体・操作・対象」を受け取るpolicyとして記述する。policy適用時は明示的な許可以外を拒否し、403を返す。存在を隠す用途では404を選択できる。
- 一覧取得でも認可済みの対象に絞り込める。所有者IDなどをリクエストから無条件に信用しない。
- Cookie認証、OAuth/OIDC、MFAは初版には含めない。標準認証でCookieを使用しない。

受け入れ条件: 登録から失効、リセットまで動作し、他ユーザーの取得・更新・一覧への混入を拒否できる。並行したリセット要求でもトークンは一度しか使えない。

### 4.4 Model・永続化

- 型付きモデルでCRUD、絞り込み、並び替え、ページングを記述できる。
- belongs-to、has-one、has-many、多対多の関連を扱える。関連の事前取得を明示できる。
- HTTP入力の必須、長さ、範囲、形式の検証はRequest型に定義する。modelにリクエスト固有の検証ルールを持たせない。
- 不正な状態遷移など、workerやrunnerからも守るべき業務上の不変条件はmodelの操作で保証する。Requestの検証成功だけを整合性の保証にしない。
- 一意性や参照整合性はDB制約で保証する。事前検証だけに依存しない。
- トランザクション、ロールバック、行ロック、コネクションプールを利用できる。
- 作成日時・更新日時を標準で管理する。更新には許可された属性だけを渡す。
- 値はバインドし、列名・並び順などバインドできない動的指定は許可リストで制限する。
- 生SQLを使う経路も提供する。
- 外部キーの削除動作を明示する。暗黙の連鎖削除や関連読み込みを行わない。
- 一覧の標準ページサイズは20、上限100とし、変更可能にする。並び順はIDなどで一意に確定させる。

受け入れ条件: 関連付きCRUD、同時挿入時の一意制約、ロールバック、事前取得、ページングを実DBで検証できる。HTTPを経由しないworker・runnerからも業務上の不変条件が守られる。

#### 4.4.1 宣言・型・DBとの対応

- modelは通常のRust structを基本とし、宣言からCRUDと型付きの列参照を生成する。業務処理は通常の`impl`に書く。独自の基底クラスやRepositoryの作成は必須にしない。
- 初版のmodel APIは単一のUUID主キー`id`を標準とする。任意の複合主キーを持つ既存テーブルは生SQLで扱えるが、自動CRUDの対象外とする。
- テーブル名は生成時にsnake_caseの複数形を明記する。実行時の複雑な単複変換には依存せず、既存テーブル・列名への明示マッピングを許可する。
- 通常modelは取得済みの列を保持し、関連データやDB接続を内部に隠して保持しない。全列が揃わない部分取得は別の結果型へ返す。
- DBの変更はmigrationを正本とし、modelの編集だけでDBを自動変更しない。model生成時は対応するmigrationも生成し、その後の変更は明示的に行う。
- NULL列は`Option<T>`、非NULL列は`T`で表現する。不一致はデコードエラーとして扱い、既定値で埋めて隠さない。

| DB上の型 | Rustでの表現方針 |
|---|---|
| uuid | UUID型 |
| boolean / integer / bigint | bool / i32 / i64 |
| text / varchar | String |
| numeric | 精度を保つDecimal型。浮動小数点へ暗黙変換しない |
| timestamptz / date | UTC日時型 / 日付型 |
| jsonb / bytea | JSON値または対応する型 / バイト列 |

具体的なUUID・Decimal・日時型は採用クレート確定時に統一する。文字列enumは明示した値へ変換し、未知の値を勝手に既定値へ変換しない。

#### 4.4.2 CRUDとquery

以下は操作名と戻り値の契約であり、ジェネリクス・引数の最終記法は実装時に確定する。DB操作は明示的な非同期呼び出しとする。

| 操作 | 契約 |
|---|---|
| find | 主キーで取得し`Result<Option<Model>, DbError>`を返す。未存在とDB障害を区別 |
| create | 許可した作成属性からINSERTし、DBの既定値を含む保存結果を返す |
| update | 指定した属性だけUPDATEし、保存結果または未存在を返す |
| delete | 主キーでDELETEし、削除したか未存在かを返す |
| query | 条件を組み立てるだけでは実行せず、fetch/count/existsなどで実行 |

- 作成・更新の属性型はmodel宣言から生成でき、アプリ側で同じ列を何度も手書きさせない。HTTP用Requestから属性への変換は明示し、所有者IDなどは認証主体から設定する。
- 新規・既存を自動判別するsave、dirty tracking、自動保存の連鎖は初版に導入しない。create/update/deleteを使い分ける。
- 更新属性は「指定なし」「値」「NULL」を区別し、NULLを指定できるのはnullable列だけとする。空の更新はSQLを発行せず入力エラーとする。
- UUIDはcreate時に生成でき、明示したIDも使用できる。created_at/updated_atは生成migrationでDBの既定値を持たせ、modelのupdateはupdated_atをDB時刻で更新する。生SQLでの更新日時管理はSQL側の責務とする。
- queryは等値・大小・IN・IS NULL、AND/OR、order、limit/offset、count、existsを提供する。列は生成された型付きの参照を使い、ユーザー文字列をSQLへ直接連結しない。
- 空のINは該当なしとする。NULL比較はIS NULL/IS NOT NULLで表現する。大きいINとpreloadはDBのパラメータ上限に収まるよう分割する。
- HTTPの一覧生成コードはページングを必須にし、pageは1以上、per_pageは1〜設定上限とする。不正値は422。has_nextは1件余分に取得して判定し、毎回のCOUNTを必須にしない。
- 一覧の並び順には一意な主キーを補い、同順位の順序を確定する。offsetページングは並行更新中のスナップショットを保証しない。
- modelの未存在を直接HTTP 404にせず、controllerが共通HTTPエラーへ変換する。CLI・workerからもHTTP非依存で使えるようにする。
- 汎用の一括更新・削除は初版の生成APIに含めない。必要な処理は条件を明示した生SQLやmodelの業務メソッドで行う。

#### 4.4.3 Association

| 関連 | 定義・DB制約 | 単件からの明示取得結果 |
|---|---|---|
| belongs_to | 参照先と外部キー。必須ならNOT NULL | 必須は関連model、任意はOption |
| has_one | 相手側の外部キー＋UNIQUE | Option |
| has_many | 相手側の外部キー | Vec。該当なしは空 |
| many_to_many | 中間modelと2本の外部キー＋組み合わせのUNIQUE | Vec。該当なしは空 |

- 関連名、参照先、外部キーを宣言する。生成時に標準名を補えるが、実行時にDB探索して推測しない。
- `task.project(&db).await?`のように明示的に取得する。フィールドアクセスやJSON化でSQLを発行しない。
- 必須belongs_toで参照先がない場合は整合性エラーとする。関連取得そのものは認可を保証せず、必要な対象範囲をqueryで絞る。
- `preload`は親の取得後に関連IDをまとめて取得する。親の件数・順序・ページ境界を変えず、親1件ごとのSQL発行を避ける。
- 通常modelには関連を載せず、preload結果を親と取得済み関連を持つ型付き結果として返す。取得済みの不存在をOptionや空Vecで表し、未取得と混同しない。具体的な戻り型の構文は実装時に確定する。
- ネストしたpreloadは明示した経路だけを取得し、自動再帰しない。関連が多い場合は関連用のページングqueryを使い、preloadで関連を黙って切り捨てない。
- preloadの関連queryにも認可用の条件を渡せる。必須関連が認可範囲から外れる場合は親も対象外にするかエラーとし、認可を外して取り直さない。
- preloadは通常複数SQLであり、並行更新中の同一スナップショットを保証しない。必要なら同じトランザクションと適切な分離レベルで取得する。
- 外部キー宣言からmigrationを暗黙変更しない。resource生成時にFKと必要なindexを生成し、has_oneはUNIQUE、中間modelは組み合わせのUNIQUEも生成する。
- 削除動作はmigrationでRESTRICTを標準に明示する。CASCADE/SET NULLは利用者が選択する。関連先の自動保存、polymorphic関連、任意のhas_many-through DSLは初版の対象外とする。多対多は明示した中間modelで提供する。

#### 4.4.4 トランザクション・競合・失敗

- poolとトランザクションを同じmodel操作へ明示的に渡せる。トランザクション中に暗黙にpoolへ戻らず、関連操作とジョブ登録も同じ接続を使う。
- begin/commit/rollbackを提供する。未commitの終了・エラー・キャンセルはrollbackし、処理済みと確認できるまで接続をpoolへ戻さない。
- 入れ子の自動トランザクションは提供しない。既存のトランザクションを渡す。savepointが必要ならDBアクセス層の明示操作を使用する。
- 分離レベルの標準はREAD COMMITTEDとし、用途に応じて指定できる。行ロックはトランザクション内で取得する。
- 読み取り→判定→更新に競合がある処理は、行ロックまたは期待する状態をWHERE条件に含めた更新を使う。汎用updateが自動で更新競合を検出するとは保証しない。
- 業務上の不変条件が必要なモデルは変更を業務メソッドへ集約し、低水準の生成CRUDを外部へ公開しない設定を提供する。生SQLはその保証を迂回する明示的な操作として扱う。
- UNIQUE/FK/CHECK違反、接続不能、pool取得timeout、デコード失敗、deadlockなどを区別する。制約名を既知の業務エラーへ対応付けでき、SQLや制約の内部名はHTTPへ出さない。
- deadlockやserialization failureを無条件に自動再試行しない。再試行する場合は副作用のないトランザクション全体を対象に、上限を指定する。commit中の接続断は結果不明として扱い、盲目的な再実行をしない。
- メール送信などの外部副作用をトランザクション内で実行しない。同じトランザクションで永続ジョブを登録し、commit後にworkerで行う。

追加の受け入れ条件: 更新の省略/NULL、DB既定値、未知enum、同時更新、FK・UNIQUE違反を検証する。preloadはパラメータ分割が不要な件数では親件数を増やしても関連SQL数が増えず、空関連・ページング・認可を維持する。業務更新とジョブ登録のcommit/rollbackが一致する。

### 4.5 DBマイグレーション・スキーマ管理

- 順序付きのマイグレーションを生成・適用・一覧表示できる。
- 適用履歴とチェックサムを記録し、適用済みファイルの改変を検出する。
- 同時実行を排他制御し、同じ変更を二重適用しない。
- PostgreSQLが許す変更はトランザクション内で適用する。非トランザクションの変更は明示する。
- ロールバック処理を定義できる。不可逆な変更はその旨を宣言し、ロールバック要求をエラーにする。
- 空DBの構築、開発・テスト用seed、スキーマの出力を提供する。
- 本番DBのリセットは標準で拒否し、明示的な環境指定と破壊操作の許可を要求する。サーバー起動時の自動マイグレーションは行わない。

受け入れ条件: 空DBへの全適用、可逆変更の巻き戻し、途中失敗後の再実行、同時実行、改変検出を検証できる。

#### 4.5.1 ファイル形式と生成

初版の設計案として、migrationはSQLを標準にする。PostgreSQLを使う前提なので、独自のschema DSLを増やさず、CLIが通常のCREATE/ALTER TABLEやindexのひな形を生成する。

```text
migrations/
  20260925000100_create_projects.up.sql
  20260925000100_create_projects.down.sql
  20260925000200_create_tasks.up.sql
  20260925000200_create_tasks.down.sql
```

- バージョンは固定桁のUTC時刻ベースの識別子とし、重複は生成時・実行時ともにエラーとする。実行順はバージョンの昇順とする。
- upを必須とし、downがなければ不可逆とする。生成した空のdownで巻き戻せると見せかけず、内容が空の場合も不可逆として扱う。
- テーブル・列・index・FK・UNIQUE・CHECK・既定値の追加/変更/削除はSQLで表現する。生成CLIの識別子は検証・引用し、入力をそのままSQLへ埋め込まない。
- 主キー、日時列、参照列の型・FK・indexは生成対象とする。業務上の制約は利用者が追加する。既存modelとの差分から本番DBを自動変更する機構は作らない。
- up/downそれぞれの先頭に`-- kouga: transaction=false`を指定した場合だけ、その方向のトランザクションを無効にする。SQL本文の内容から自動推測しない。
- 通常ファイル内のBEGIN/COMMITは不要とし、実行器が境界を管理する。SQLを単純なセミコロン分割で処理せず、SQL対応の既存実行機構を利用する。

#### 4.5.2 適用履歴・排他・失敗復旧

- 専用の履歴テーブルにversion、名前、up/downのチェックサム、実行モード、状態、適用日時を保存する。checksumは実行するファイル内容から算出する。
- 実行前に全ファイルの重複・組み合わせ・適用済みchecksum・欠落を検査する。適用済みの改変や削除はエラーとし、履歴を黙って書き換えない。
- 適用済み最大versionより古い未適用ファイルは順序不整合として拒否し、新しいversionへ付け直して適用する。
- migrate/rollback/resetは同じDBで共通の排他を取得する。専用接続のsession advisory lockをコマンド全体で保持し、ロック待機にはtimeoutを設ける。
- 標準は1 migrationにつき1トランザクションとし、DDLと適用履歴を同時にcommitする。失敗したmigrationのみrollbackし、先に完了したmigrationは保持して後続を中止する。
- 非トランザクションmigrationは実行前にdirty状態を永続化し、成功後に適用済みへ更新する。失敗・強制終了ではdirtyを残して、以降のmigrate/rollbackを停止する。
- 非トランザクション処理の中断後は、DB上の部分的な変更を自動的に元へ戻したり再実行したりしない。`db status`で対象を示し、利用者が修復SQLを実行して実際の状態を確認する。
- 復旧用の`kouga db repair --version <id> --state applied|pending`を提供する。dirtyな対象に限り、排他下で履歴状態を修復する。SQLは実行せず、理由の指定を必須にして記録する。appliedはup完了、pendingは未適用相当へ復旧済みであることを利用者が確認する。
- repairでchecksumの不一致を無視したり正常な履歴を変更したりできない。元ファイルを復元し、修正は新しいmigrationとして追加する。

#### 4.5.3 CLI・rollback・schema・seed

| コマンド | 詳細 |
|---|---|
| `kouga generate migration <name>` | 新しいversionのSQLひな形を生成 |
| `kouga db migrate` | 検証後、未適用分を昇順で適用。対象なしは成功 |
| `kouga db rollback --steps <n>` | 標準1件。適用済みの最新から逆順にdownを適用 |
| `kouga db status` | pending/applied/dirty・不可逆・checksum不一致を表示 |
| `kouga db schema` | 現在のDBから`db/schema.sql`へschemaを出力 |
| `kouga db seed` | 現在のmodel APIを使う登録済みseed処理を実行 |
| `kouga db reset` | 開発・テストDBを再作成しmigrationを全適用。seedは明示指定 |
| `kouga db repair ...` | 手動復旧済みのdirty履歴を修復 |

- rollbackは対象全件のdownとchecksumを実行前に検査し、不可逆が含まれる場合は何も変更しない。実行中の失敗はそこで停止し、既に完了した巻き戻しは戻さない。
- down成功時は履歴を未適用相当へ戻す。非トランザクションのdown失敗もdirtyとして停止する。downがデータを復元できるとは保証しない。
- schema出力は標準のPostgreSQLツールを利用し、所有者・権限・データを含めない。必要なツールと対応バージョンを文書化する。schema.sqlは確認用の生成物とし、初版のDB構築経路はmigrationの全適用に統一する。
- seedはDDLや適用履歴を変更しない。開発用サンプルデータと本番の初期データを分け、再実行を想定するseedは一意キーなどで冪等にする。schema変更時の既存データ移行は、当時の列を直接扱うSQLか明示したrunner処理にする。
- resetは接続先のDB名・環境を表示し、対象を明示させる。本番は専用の破壊操作許可を必須とし、通常の起動やデプロイから呼ばない。
- lock_timeoutとstatement_timeoutを設定できる。大きなテーブルの変更は、追加→データ補完→制約適用→旧列削除を分ける。migrationのSQLが無停止・低負荷で実行できることまでは保証しない。

非トランザクション指定の代表例は`CREATE INDEX CONCURRENTLY`とする。DB制約・index・排他の詳細はPostgreSQLの仕様に従う。参照: [制約](https://www.postgresql.org/docs/current/ddl-constraints.html)、[CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)、[ロック](https://www.postgresql.org/docs/current/explicit-locking.html)。

追加の受け入れ条件: 重複version・適用済み改変・欠落・順序不整合でSQL実行前に停止する。2プロセスの同時適用でも一度だけ適用される。通常DDLの失敗と非トランザクションDDLの中断を分けて再現し、dirty検出・手動修復後の継続を確認する。rollback対象に不可逆がある場合は全件未変更とする。

### 4.6 Request validation・Controller

- `requests/`に操作ごとのRequest型を定義し、パス・クエリ・JSON・multipartの入力項目と検証ルールをまとめる。
- Request型の指定により、フレームワークが入力抽出・型変換・検証をcontroller呼び出し前に自動実行する。controller内での手動のvalidate呼び出しを標準にしない。
- 必須、長さ、範囲、形式、項目間の条件、独自ルールを扱い、フィールド単位のエラーを返す。再利用する検証ルールはmodelから独立した関数や型として定義できる。
- DB参照を伴う非同期検証にも対応する。存在・一意性の事前検証は補助であり、認可やDB制約の代わりにはしない。
- 検証済み入力は型で区別し、通常の公開APIでは未検証入力から直接構築できない。actionの引数として宣言することで、検証済みの値だけを受け取れるようにする。具体的なRust APIは実装着手時に確定する。
- 作成用と更新用のRequest型を分けられる。更新では「省略」と「明示的なnull」を区別する。
- Request型とDBモデルを分け、許可していない属性の更新を防ぐ。JSONの未知フィールドは標準で拒否する。
- controllerは検証済み入力を使って対象リソースの認可とmodel操作を行い、型付きレスポンスまたは共通エラーを返す。対象の取得は認可された範囲に限定する。
- 認証主体、DB、設定などのアプリ状態へアクセスできる。
- 構文・型・未知フィールドの不正は400、非対応Content-Typeは415、Requestの検証ルール違反は422とする。失敗時はcontrollerを呼び出さない。
- JSON API以外に、ファイルのストリーミング応答とWebSocketへのupgradeを扱える。

受け入れ条件: middleware → request validation → controllerの実行順を検証できる。不正な型・未知属性・検証ルール違反ではcontrollerの処理と書き込みが実行されない。作成と更新で異なるルールを適用でき、PATCHで省略とnullを区別する。認証必須ルートでは未認証の入力検証を実行しない。

#### 4.6.1 覚える概念を絞ったvalidation

基本は「Rustの型」「少数の組み込みルール」「普通のRust関数」の3つに絞る。ルールを文字列で連結する別言語や、validatorごとのクラス・trait実装を要求しない。以下の属性・型名は公開APIの設計案とする。

```rust,ignore
#[derive(Request)]
struct CreateProjectRequest {
    #[validate(length(min = 1, max = 100))]
    name: String,

    #[validate(custom = validate_slug)]
    #[schema(description = "小文字英数字とハイフン。予約語は使用不可")]
    slug: String,
}

fn validate_slug(value: &str) -> Result<(), ValidationError> {
    if value.is_empty() || value == "admin"
        || !value.bytes().all(|c| c.is_ascii_lowercase() || c.is_ascii_digit() || c == b'-')
    {
        return Err(ValidationError::new("invalid_slug"));
    }
    Ok(())
}
```

| 基本機能 | 定義方法・意味 |
|---|---|
| 型・必須 | 作成Requestの`T`は必須かつ非null。別のrequired指定は不要 |
| 任意 | 作成Requestの`Option<T>`は省略/nullをNoneとして扱う |
| PATCH | `Patch<T>`のMissing/Value、nullableなら`Patch<Option<T>>`のMissing/Value(None)/Value(Some)。専用型はこの用途だけ |
| 長さ | `length(min, max)`。文字列はUnicodeスカラー値数、配列は要素数。バイト長・表示上の文字数とは区別 |
| 数値範囲 | `range(min, max)`。境界を含む。整数などの型範囲は型変換時に検査 |
| 選択肢 | Rustのenumで表現し、別のinルールは不要 |
| メール形式 | `email`。既存実装で構文を検査し、到達可能性は保証しない |
| その他 | `custom = 関数名`で接続する |

- Stringの必須と空文字禁止は別とする。空文字禁止はlength(min = 1)、空白のみの禁止はカスタム検証で指定する。trim・大小文字変換などの暗黙の書き換えをしない。
- OptionがNone、PATCHがMissingのときは値に対するルールを実行しない。null禁止列にnullが来た場合は型不正として400を返す。空PATCHはRequest全体の検証で422にする。
- 処理順は、入力抽出・型変換 → 組み込みと同期カスタム検証 → 非同期カスタム検証とする。前段にエラーがあれば次段とcontrollerを実行しない。
- 同期カスタムは値を受け取って`Result<(), ValidationError>`を返す。項目間条件はRequest全体を受け取る関数として同じcustom指定で登録し、対象フィールドのpathを返せる。
- DB参照などが必要な場合だけ`custom_async`を使い、値またはRequestと検証contextを受け取る非同期関数にする。contextはDBと認証主体へアクセスできる。自動のDB書き込みや外部副作用は行わない。
- 非同期検証は標準で順に実行し、リクエスト全体のtimeout内で処理する。入力件数に応じて無制限にタスクを生成しない。
- 検証失敗と基盤障害は別のエラーとする。DB停止を「値が不正」という422へ変換せず503にする。内部の不具合は500とする。
- 同期段階で得られるエラーはフィールド宣言順・ルール順で収集する。非同期段階でも同じ順序を保ち、基盤障害では中止する。エラー件数とネストの深さに上限を設ける。
- エラーは安定したcodeとfield pathを持つ。配列内は`items[0].name`のように示し、入力値そのもの、特に秘密情報を返さない。
- ネストした入力も同じRequest由来の検証機構を利用し、validatorを別ファイルへ分けることは強制しない。複数Requestで再利用するときに普通のモジュールへ移せる。
- 検証済み型は`Validated<T>`を基本案とする。内部値の変更用アクセスや未検証の公開constructorは提供しない。controllerの引数抽出が生成し、HTTP以外では同じ検証関数を呼ぶ公開経路で生成できる。
- 組み込みルールは同じメタデータを実行時検証とOpenAPIで共有する。customはschemaの説明を補足する。新しいルールを組み込みへ昇格させるためのプラグイン機構は初版には設けない。

追加の受け入れ条件: 標準ルールだけのRequest、単一項目custom、項目間custom、DB参照custom_asyncを同じ仕組みで扱える。PATCHの3状態、日本語の長さ、エラー順序、非同期検証の前段失敗時スキップ、認証主体による参照範囲、DB障害を検証する。検証済み型を未検証入力から直接構築・変更するコードはコンパイルできない。

### 4.7 JSONレスポンス

- 公開用の出力型でレスポンスを定義する。モデルの全属性を自動公開しない。
- 日時はUTCのRFC 3339、UUIDは文字列、金額など精度が必要な小数は文字列で表現する。
- 単件は`{"data": {...}}`、一覧は`{"data": [...], "meta": {"page": 1, "per_page": 20, "has_next": false}}`を生成コードの標準とする。
- 作成は201とLocation、取得・更新は200、本文なしの削除は204を標準とする。
- アプリ固有の出力型、ステータス、ヘッダーも指定できる。

受け入れ条件: 単件・一覧・空一覧・204の形式を検証でき、パスワードハッシュやトークンが混入しない。

### 4.8 エラーハンドリング

- エラー形式は`{"error": {"code": "validation_failed", "message": "...", "details": [{"field": "email", "code": "invalid"}]}, "request_id": "..."}`とする。
- `code`は機械判読用の安定した値とし、`message`の文言には依存させない。`details`は不要なら省略できる。
- 400/401/403/404/405/409/413/415/422/429/500/503/504を共通の型から生成できる。
- 既知のDB制約違反は422または409へ明示的に変換し、未知のDBエラーを一律にクライアントの責任にしない。
- 未処理エラーは500、依存先の一時的な利用不能は503、要求タイムアウトは504とする。
- 本番レスポンスにはSQL、秘密情報、スタックトレースを含めない。詳細はrequest IDとともにログへ記録する。

受け入れ条件: middleware・request validation・controllerのいずれで発生しても共通形式となり、内部情報を外部へ漏らさず追跡できる。

### 4.9 Mailer

- 型付き引数から宛先・件名・テキスト本文・HTML本文・添付ファイルを組み立てる。
- HTML本文では動的な値を標準でエスケープし、ヘッダーへの改行注入を拒否する。
- SMTPで即時送信でき、queue経由で非同期送信できる。
- 標準の非同期構成では、SMTP実装・テンプレート・添付の取得処理をworker側だけへ含める。HTTP側は共有したメールジョブの引数を投入する。
- 本番のSMTPではTLSと証明書検証を必須とする。ローカル検証用の例外は明示設定とする。
- 開発・テストでは外部送信せず、生成したメールを検査できる。
- 非同期送信の再試行はqueueの規則に従う。送信結果が不明な障害では重複送信があり得ることをAPIドキュメントに記載する。

受け入れ条件: テキスト・HTML・添付を生成し、テスト用SMTPへの送信、非同期送信、送信失敗からの再試行を検証できる。

### 4.10 Queue・Worker

- 型付き引数のジョブをDBへ永続化し、即時実行・指定時刻以降の実行・名前付きqueueを指定できる。
- ジョブの契約と投入APIをhandler実装から分離し、worker側でhandlerを登録する。常駐モードに加え、第3.3節のワンショット実行モードを提供する。
- workerの並列数と購読queueを設定できる。ジョブ種別とpayloadのバージョンを保存する。
- 複数workerで取得を排他制御し、leaseとheartbeatによって実行権を管理する。期限切れジョブは再取得可能にする。
- 完了・失敗の更新は実行権を持つworkerのみが行える。ただし期限切れ後も旧処理が動く可能性があるため、副作用の一度限りの実行は保証しない。
- 配信保証はat-least-onceとする。ジョブ側で冪等性キーやDB制約を使えるよう、安定したjob IDを提供する。
- 指数バックオフとジッターで再試行し、上限到達後はdead状態にする。試行回数、エラー、次回実行時刻を記録する。
- タイムアウト、待機中ジョブのキャンセル、失敗一覧、手動再投入を提供する。未知の種別・非対応payloadは理由付きで隔離する。
- 同じDBの業務更新とジョブ登録を、同一トランザクションで確定できる。
- 終了時は新規取得を止め、猶予時間内の完了を待つ。未完了分はlease満了後に再実行できる。
- 定期実行は初版では外部スケジューラーからCLIで投入する方式とし、内蔵cronは設けない。

受け入れ条件: 複数worker、実行途中の強制終了、再取得、retry上限、手動再投入、業務更新と登録の同時rollbackを検証できる。

### 4.11 キャッシュ

- get/set/delete/fetch、TTL、キーの名前空間を提供する。
- 開発・テスト用のプロセスメモリと、複数プロセス用のPostgreSQL保存を提供する。
- 期限切れの値は返さず、期限切れレコードを定期清掃できる。メモリ版には容量上限を設ける。
- fetchはmiss時に値を生成する。同時miss時の重複計算は許容し、業務処理の一度限りの実行には利用させない。
- キャッシュ障害時は警告を記録して元データを取得できる。認可やレート制限など、失敗時に許可してはいけない処理はこの縮退動作を利用しない。

受け入れ条件: TTL、削除、名前空間、容量上限、プロセス間共有、ストア障害時の動作を検証できる。

### 4.12 ファイルアップロード・ストレージ

- multipartアップロードとストリーミング保存を提供する。ファイル全体のメモリ読み込みを前提にしない。
- ローカルとS3互換ストレージを同じアプリケーション操作で利用できる。
- メタデータとモデルへの関連をDBで管理する。サイズ上限と許可するファイル種別を設定でき、申告Content-Typeだけに依存しない。
- 保存キーはサーバー側で生成し、元ファイル名をパスに使用しない。標準は非公開とする。
- ダウンロード時に認可し、ローカルはアプリ経由、オブジェクトストレージは短期限の署名付きURLも利用できる。
- ダウンロードはattachmentを標準とし、Content-Typeとnosniffを適切に設定する。
- DBとストレージは同一トランザクションにならないため、未関連ファイルの期限付き清掃と削除失敗の再試行を提供する。
- 画像変換、ウイルススキャン、ブラウザからの直接アップロードは初版には含めない。

受け入れ条件: 両ストレージで保存・取得・削除が動作し、サイズ超過、パストラバーサル、無認可アクセス、途中失敗後の残骸を扱える。

### 4.13 WebSocket

- channel単位の購読・解除、クライアントからの受信、認可された購読者への配信を提供する。
- 接続時の認証とOrigin検証、購読時・操作時の認可を行う。
- ブラウザ向けには、認証済みHTTP APIで短期限・一度限りの接続ticketを発行する。長期BearerトークンをURLへ載せず、ticketもログから除外する。
- 認証期限・失効を定期確認し、無効な接続を切断する。確認間隔を設定できる。
- PostgreSQLの通知機構で複数サーバー間の配信を連携する。通知サイズ上限を超えるメッセージは送信前にエラーとする。
- メッセージサイズ、接続数、送信待ちバッファに上限を設け、遅いクライアントは切断する。heartbeatで切断を検知する。
- 配信はオンライン接続へのbest-effortとする。切断中の履歴再送・永続配信は初版には含めず、再接続後の状態はHTTP APIで取得する。

受け入れ条件: 別サーバーに接続した購読者へ届き、不正ticket、許可されないOrigin・購読・操作、期限切れ、遅い受信者を処理できる。

### 4.14 設定・シークレット管理

- development/test/productionを区別し、型付き設定を起動時に検証する。
- 優先順位は環境変数 > 環境別設定ファイル > 共通設定ファイル > 既定値とする。
- 秘密情報は環境変数または参照先ファイルから取得する。両方が指定された場合は曖昧さを避けて起動エラーにする。
- 必須設定の欠落・形式不正は起動時エラーにする。秘密情報をDebug表示や設定一覧へ出さない。
- 暗号化credentialsファイルの独自管理は初版に含めない。デプロイ先の秘密情報管理から値を注入できる構成とする。

受け入れ条件: 環境別上書き、秘密ファイルの読み込み、欠落・競合の拒否、ログの秘匿を検証できる。

### 4.15 ログ・計測・稼働状態

- 構造化ログを標準出力へ出し、レベル、時刻、request IDまたはjob ID、処理時間を含める。
- Authorization、パスワード、トークン、接続文字列をマスクする。リクエスト本文とクエリ値は標準で記録しない。
- HTTP、DB操作、ジョブ、メール送信の計測点を提供する。
- HTTP件数・時間・エラー率、DB pool使用状況、ジョブ待機数・失敗数・待機時間を収集できる。
- メトリクスのラベルにユーザーIDや生パスを使わず、ルート定義などの有限な値を使う。
- livenessとreadinessを分ける。readinessはDBなど必須依存先を確認し、失敗時は503を返す。
- メトリクスは管理用経路へ公開し、ネットワーク制限または認証を設定できる。

受け入れ条件: HTTPからDB・ジョブ登録まで追跡でき、機密情報が出力されず、依存先停止時にreadinessが失敗する。

#### 4.15.1 OpenTelemetryと独自の計測

OpenTelemetry（OTel）を任意で組み込めるようにする。ログの出力先変更に加えて、trace（処理の流れと時間）・metrics（件数や時間の集計）・logs（出来事の記録）を関連付けて外部へ送る。保存・可視化するバックエンドはKougaに内蔵しない。

- 通常の構造化ログとspanにはRustの`tracing`を利用する。利用者は`tracing::info!`や`#[tracing::instrument(skip_all)]`で独自のログ・計測を追加でき、Kouga専用のloggerクラスは要求しない。
- OTel SDK・exporterは任意依存として分離する。利用しないHTTP/workerイメージには含めない。有効化にはビルド時の依存追加と実行時の設定の両方が必要とし、環境変数だけで未搭載のSDKを有効化できるとは扱わない。
- 導入UIの案として`kouga add otel`を提供する。既存HTTP/workerパッケージの依存と起動処理に標準の統合を追加し、差分を表示する。編集済み箇所を安全に更新できない場合は必要な変更を表示し、黙って上書きしない。後から生成するworkerにも選択済みの統合を引き継ぐ。対象を限定する具体的な記法は実装時に確定する。
- OTLP/HTTP protobufによるtraces・metrics・logsの送信を提供する。初版で対応する設定はOTEL_SERVICE_NAME、OTEL_RESOURCE_ATTRIBUTES、OTEL_EXPORTER_OTLP_ENDPOINT、OTEL_EXPORTER_OTLP_HEADERS、各signalのexporter有効/無効、sampling設定を明記する。全SDK環境変数への無条件の対応は約束しない。
- 標準ログ出力は維持する。OTel依存追加後もendpoint未設定なら外部送信しない。endpoint指定時の標準はtraces・metricsのOTLP送信とし、logsのOTLP送信は明示指定で有効化する。標準出力の収集とOTLP logsの二重取り込みを避けられるようにする。
- HTTP/workerに別のservice.nameを設定し、service.versionと環境名も指定できる。request ID・job IDに加え、有効なtrace contextがあるログにtrace_id/span_idを付ける。request IDをtrace IDの代用にしない。
- 標準計測はHTTP受付、Kouga経由のDB操作、ジョブ投入・実行、メール送信とする。対応する外向きHTTPクライアントへcontextを伝播する。直接使う外部クレートや生SQLの任意呼び出しまで自動計測すると約束しない。
- HTTPのtraceparent/tracestateは形式を検査する。受信contextを親にする信頼範囲を設定でき、不正または信頼しない入力は新しいtraceとして処理する。trace情報を認証・認可に使用しない。baggageは標準で伝播せず、必要時は許可リストとサイズ上限を設ける。
- ジョブ投入時のcontextを業務payloadと分離したmetadataへ保存する。workerは試行ごとに新しい実行spanを作り、投入contextへspan linkで関連付ける。遅延実行中ずっとHTTP spanを開いたままにしない。contextがない既存ジョブも処理できる。
- retryの各試行は同じjob IDと試行番号で区別し、別spanとして記録する。非同期タスクには明示的にspanを引き継ぎ、thread localへの依存やawaitをまたぐenter guardで処理を混同しない。
- 標準の秘匿方針を全signalへ適用する。SQLパラメータ、本文、認証情報、メール宛先などは自動記録しない。利用者が独自に記録する値まで完全に自動秘匿できるとは保証せず、生成例ではskip_allと必要な項目の明示指定を使う。
- サンプリングとログのレベルフィルターは分ける。メトリクスのラベル数を制限し、ユーザーID・job ID・trace IDをラベルにしない。
- 送信は上限付きのバッファ・timeout・再試行を使う。Collectorの障害で業務リクエストやジョブを失敗させず、上限時には計測データを破棄して警告・破棄数を記録する。永続的な監査ログの代用にはしない。
- graceful shutdownとワンショット終了時に上限時間内でflushする。Lambdaではinvocation終了前のflushを統合し、プロセス終了だけに頼らない。強制終了時の配送保証はしない。
- 初期化は実行ファイルの起動時に一度行い、ライブラリが勝手にglobal subscriber/providerを設定しない。標準の初期化を使うか、利用者がsubscriber/layer/providerを構成して起動処理へ渡すかを選べる。二重初期化とexporter内部ログの再取り込みを防ぐ。

受け入れ条件: OTel未搭載の依存グラフと通常ログを確認する。有効化したHTTP→DB→ジョブ投入→別worker→メールの関連をテスト用Collectorで確認し、カスタムspan・logs送信・metricsも検証する。並行リクエスト間のcontext混入、再試行の区別、機密情報の非記録、送信先停止時の業務継続・バッファ上限、ワンショットのflushを検証する。Rust SDKの採用バージョンと対応機能は実装時に固定する。

参照: [OpenTelemetryのsignals](https://opentelemetry.io/docs/concepts/signals/)、[SDK環境変数](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/)、[OTLP設定](https://opentelemetry.io/docs/specs/otel/protocol/exporter/)、[Rust tracing](https://docs.rs/tracing/latest/tracing/)。

### 4.16 テスト支援

- 実ポートを開かずにルーティングからレスポンスまで実行するリクエストテストを提供する。
- テスト用DBの構築・マイグレーション・後片付けを支援し、並列テストのデータを分離する。
- メール記録、ジョブ投入の検査・手動実行、一時ストレージ、メモリキャッシュを提供する。
- 認証済みリクエストを簡単に作れる。ただし認可処理は省略しない。
- TTLと遅延ジョブを長時間待たずに検証できる手段を提供する。
- DB・SMTP・オブジェクトストレージ・複数プロセスの結合テストも用意し、代替実装だけで完了扱いにしない。
- `cargo test`を標準入口とし、外部サービスが必要なテストの起動手順を明記する。

受け入れ条件: 生成したCRUD APIの正常系・認証失敗・認可失敗・入力不正・DB失敗を、独立して再現できる。

### 4.17 CLI・コード生成・コンソール

CLI名は`kouga`とする（ユーザー指定）。以下を提供する。

| コマンド | 用途 |
|---|---|
| `kouga new <name>` | ビルド・起動可能なAPIアプリを作成 |
| `kouga new <name> --api grpc` | gRPCのみの構成でアプリを作成（操作案） |
| `kouga add http` / `kouga add grpc` | 既存の入口を維持して別の入口を追加（操作案） |
| `kouga server [--api http\|grpc]` | 選択した入口のサーバーとマルチスレッド版Tokioを起動 |
| `kouga routes` | メソッド・パス・actionを一覧表示 |
| `kouga add otel` | 任意のOpenTelemetry統合を生成アプリへ追加（操作案） |
| `kouga openapi generate` | アプリルートに`openapi.yml`を生成・更新 |
| `kouga openapi check` | 生成結果と既存ファイルの一致・仕様の妥当性を検査 |
| `kouga generate model/request/controller/resource/migration/middleware/mailer/job/channel/auth` | 必要なコードを生成 |
| `kouga db create/migrate/rollback/status/schema/seed/reset/repair` | DB管理 |
| `kouga worker` | queue workerを起動 |
| `kouga jobs list/show/retry/cancel/enqueue` | ジョブ確認・操作 |
| `kouga maintenance` | キャッシュ・失効token・未関連ファイルなどを清掃 |
| `kouga console` | アプリの設定でDB用の対話SQLクライアントを起動 |
| `kouga runner <task>` | アプリ状態を使う登録済みRust処理を実行 |

- `resource`生成はmodel、migration、controller、作成・更新用Request型と検証ルール、出力型、route、リクエストテストを揃える。生成controllerは検証済みRequestを受け取り、入力検証を手動で呼び出さない。
- 生成したresource・authのルートと型は、そのままOpenAPI生成の対象になる。別途YAMLを記述する必要はない。
- `generate middleware`は通常の非同期関数と登録例を生成する。`generate auth`は認証middleware・CurrentUser・認証ルート・Request型とmodel/migrationを揃える。
- 生成コードは通常のRustコードとして編集できる。変更内容の事前表示ができ、既存ファイルは標準で上書きしない。
- 複数ファイルの生成前に衝突を検査する。routeへの登録を安全に自動編集できない場合は、必要な差分を表示する。
- `console`はRailsのRuby REPLと同等ではない。Rust式の対話評価は提供せず、アプリコードの実行は`runner`が担う。SQLクライアントがなければ導入手順を示す。
- CLIは失敗時に非ゼロで終了する。コマンド引数やログに秘密情報を露出させない。

受け入れ条件: 新規作成からDB構築、resource生成、テスト、HTTP起動、worker起動まで、文書化したコマンドで再現できる。

### 4.18 OpenAPI自動生成

FastAPIのように、APIの実装で宣言する情報から仕様を生成する開発体験を提供する。初版の出力はOpenAPI 3.1.1形式の`openapi.yml`とし、手書きのYAMLを正本にしない。

- HTTPルート登録時のメタデータ、Request型と検証ルール、公開レスポンス型を生成元とする。Rustの任意の処理から仕様を推測する仕組みにはしない。
- パス・メソッド、operation ID、パス・クエリ・ヘッダーのパラメータ、JSON・multipartの本文、レスポンスのステータス・ヘッダー・Content-Typeを出力する。
- 必須項目、null許容、配列、enum、長さ・範囲など、表現可能な検証ルールを反映する。PATCHの省略可能とnull許容を区別し、未知フィールドの拒否も反映する。
- 実際のシリアライズ名・出力形式に合わせる。DBモデルの全属性から生成せず、入出力型からそれぞれのschemaを生成する。共通型はcomponentsへまとめる。
- 生成コードのdata/meta形式、201とLocation、本文のない204、共通エラー形式を含める。適用middleware・Request検証に伴う既知のエラーレスポンスも反映する。
- Bearer認証のsecurity schemeとルートごとの認証要否を、実行時にも使用する宣言から生成する。policyの具体的な認可条件は説明として補足できる。
- 任意の分岐によるレスポンスや独自middlewareなど、型と標準メタデータから判断できないものは、該当コードの近くに補足情報を宣言する。型情報の不足や重複operation ID、未解決の参照は生成エラーにする。
- DB参照や独自の検証関数などschemaで表現できない条件は、説明を付けてサーバー側の検証として明示する。未対応ルールを自動変換したと扱わず、説明の不足は警告する。
- summary、description、tags、examples、deprecatedを型・ルートの近くで指定できる。認証情報などの実データを例として自動採取しない。
- `kouga openapi generate`で明示的に生成でき、開発環境の`kouga server`起動時にも自動更新する。出力先は変更可能とする。本番起動時にソースディレクトリへの書き込みを要求しない。
- 生成はルートと型の登録情報だけで完結させ、DB接続・秘密情報・controllerの実行を要求しない。ビルド済みコードの利用は許容する。
- 同じ定義から同じ内容を生成し、順序や生成時刻による不要な差分を出さない。成功後にファイルを置き換え、生成失敗時は既存ファイルを保持する。
- `kouga openapi check`はファイルを変更せず、不在・差分・仕様不正で非ゼロ終了する。CIで更新漏れを検出できる。
- 開発環境では`/openapi.yml`と、仕様を閲覧・試行できる`/docs`を提供する。UIは既存のOpenAPI対応ビューアを利用する。本番では両方を標準で無効にし、明示的に有効化・アクセス制限できる。
- 管理用・ドキュメント用ルートは標準で生成対象から除外する。業務ルートは明示的に除外しない限り対象とし、除外は認可の代わりにはしない。
- WebSocketについてはHTTP接続開始用の経路を説明できる。接続後のメッセージプロトコルは別途文書化し、HTTP APIのschemaとして誤って表現しない。

受け入れ条件: resource生成だけでCRUDのOpenAPIが生成される。Requestの必須・長さ制約、PATCHの省略/null、公開レスポンス型、認証要否の変更が出力へ反映される。生成物の仕様検証と、代表的な正常・エラーレスポンスのschema検証が通る。外部サービスなしで生成でき、連続生成で差分がなく、checkが更新漏れを検知する。開発用UIから認証付きAPIを試行でき、本番の標準設定では仕様とUIを公開しない。

出力形式の参照: [OpenAPI Specification 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)。

### 4.19 HTTPとgRPCの同居

同一のCargo workspaceでHTTP/JSONとgRPC/Protobufを提供できることを、初版の必須要件とする。利用者向けドキュメントの入口でも、この特徴を明示する。

- HTTPのみ・gRPCのみ・両方の構成を選べる。既存の入口を削除せず後から追加でき、依存・起動処理・Docker targetを必要な分だけ生成する。追加済みの場合は重複生成せず、編集済みファイルを無断で上書きしない。
- 同居は同一プロジェクトと共通業務コードを意味する。標準では別プロセス・別ポート・別イメージで実行する。同一プロセスでの統合起動や同一ポートの多重化は初版の必須要件にしない。
- HTTPはRustのRequest・公開出力型からOpenAPIを生成する。gRPCは`.proto`を契約とし、既存のProtobuf生成機構とgRPCライブラリを利用する。独自の通信プロトコル実装は作らない。
- gRPCの入口はmetadataの認証 → 入力検証 → handler → 共通業務処理・modelとする。HTTPのmiddlewareやRequest型をそのままgRPCへ強制せず、検証関数・認証の照合処理・認可policyを再利用する。
- 型のデコードが成功しただけでは業務上妥当としない。Protobufの既定値・presenceを踏まえて検証し、更新で省略を扱う場合は契約で表現する。詳細な生成記法は実装時に確定する。
- 共通業務コードはHTTP/gRPCのrequest・response・status型へ依存しない。controllerとhandlerが入出力を変換する。単純な処理ではmodelを直接呼んでよく、専用サービスクラスの作成は必須にしない。
- 認証・認可・サイズ上限・deadline・キャンセル・過負荷制御はgRPC側にも適用する。HTTP statusの数値をgRPC statusとして返さず、業務エラーと基盤エラーを区別して対応付ける。
- model・migration・トランザクション・queue投入・worker・mailerを共有できる。gRPCで登録したジョブも同じworkerが処理する。OTelはgRPCの受付・status・contextを計測し、DBとジョブへの関連を保持する。
- 初版では少なくともunary RPCを必須とする。streamingの対応範囲・reflection・grpc-web・クライアント生成支援は詳細設計時に区別し、未対応のものを対応済みと案内しない。OpenAPIと.protoの自動相互変換は要求しない。
- HTTP向けLambda adapterなどの配備対応をgRPCへ流用できるとは保証しない。ネイティブgRPCの配備に必要なHTTP/2・TLS・負荷分散の設定を別途文書化する。

受け入れ条件: HTTPで作成したアプリへgRPCを追加し、既存のAPIが維持される。両方の入口から同じ業務操作を呼び、DB整合性・認可・ジョブ投入を検証する。gRPCのみの作成とHTTPの後付けも検証する。HTTP/grpc targetを独立してビルドし、不要な入口の実装・依存が混入しないことを確認する。

## 5. 非機能要件

- サポート対象はLinuxでの本番実行と、Linux/macOSでの開発とする。Rustの最低対応バージョンと依存関係は実装時に固定・明記する。
- HTTPの受付停止と処理中リクエストの待機を行うgraceful shutdownを提供する。猶予時間は設定可能にする。
- リクエスト本文、DB pool、queueの並列数、WebSocketバッファなどの資源に有限な上限を設ける。
- HTTP・workerを複数プロセスに増やしても、認証、ジョブ、共有キャッシュ、配信が機能する。
- DB停止時に成功応答を返さず、未確定の処理を成功扱いにしない。タイムアウトは既に確定した副作用を取り消す保証にはしない。
- 本番の外部通信はHTTPSを前提とし、TLS終端はリバースプロキシでもよい。
- 性能は固定環境でJSON応答、DB単件取得、CRUD、ジョブ処理を計測し、throughput・p50/p95/p99・メモリ・条件を記録する。根拠のない目標値やRailsより高速という保証は置かない。
- 公開API、生成コード、設定、各機能の失敗時の振る舞いを文書化する。初版公開時に互換性方針を定める。

## 6. 全体の受け入れシナリオ

サンプルとして「ユーザーが自分のプロジェクトとタスクを管理するAPI」を作る。以下を一つの生成アプリで検証し、全機能がつながったことを確認する。

1. CLIでアプリを生成し、設定・マイグレーション・seed・テストを実行する。
2. 登録・ログインし、自分のプロジェクトとタスクをCRUDする。他ユーザーの操作は拒否する。
3. 不正入力・未知属性はrequest validationで拒否し、controllerが呼ばれないことを確認する。重複データは並行書き込みでもDB制約で拒否し、いずれも所定のJSONエラーを返す。
4. 関連の事前取得とページングでタスク一覧を返し、集計値をキャッシュする。更新後は集計キャッシュを無効化する。
5. タスクの作成と通知ジョブの登録を同一トランザクションで行い、workerからメールを送る。
6. workerを処理途中で停止し、再取得・再試行を確認する。冪等性を備えたDB更新が重複しないことを確認する。
7. 添付ファイルを保存し、所有者だけがダウンロードできる。削除失敗を再試行する。
8. WebSocketで変更通知を受ける。別HTTPプロセスからの変更も届き、認可外の購読は拒否する。
9. パスワードリセット後に旧tokenが使えず、WebSocket接続も所定の確認間隔内に切断される。
10. HTTPとworkerのログ・メトリクスを確認し、DB停止、レート超過、終了処理を検証する。
11. 自動生成された`openapi.yml`と開発用UIからCRUD・認証・添付APIを確認する。Requestの制約変更後に`kouga openapi check`が差分を検知し、再生成後に成功する。
12. HTTPとworkerの個別イメージを起動して連携を確認し、それぞれの依存・サイズを記録する。HTTPを更新せずworkerを更新して旧payloadを処理でき、ワンショットタスクが所定の条件で終了することを確認する。
13. OTelを追加し、HTTPとworkerを別service.nameで起動する。独自ログ・spanとジョブの関連が確認でき、Collector停止時にもAPI・workerが動作を継続することを確認する。
14. 同じアプリにgRPCを追加し、HTTPとgRPCから共通の業務処理を呼ぶ。それぞれの入力検証・認証・認可・エラー変換を確認し、gRPCを個別イメージとしてビルドする。

## 7. 実装順序と完成条件

worktreeごとの担当範囲・依存関係・検証条件は[開発タスク一覧](development-tasks.md)を参照する。以下は機能段階の全体像とする。

| 段階 | 実装範囲 | 完成条件 |
|---|---|---|
| 1 | Tokio実行基盤、設定、router、middleware、request validation、controller、JSON、エラー、ログ、OpenAPI生成、最小CLI・テスト支援 | 生成アプリで型付きAPIが起動し、非同期実行・過負荷制御・controller実行前の入力検証とOpenAPIへの反映を確認できる |
| 2 | model、migration、DB参照を伴う入力検証、resource生成、DBテスト支援 | 関連付きCRUDを生成して実DBで検証できる |
| 3 | 認証・認可、queue・worker、mailer、HTTP/workerの個別イメージ | 権限付きCRUD、永続ジョブ、非同期メールが依存を分離したイメージ間で動作する |
| 4 | キャッシュ、ストレージ、WebSocket、gRPCとHTTPの同居 | 共有状態・添付・通知が動作し、HTTP/gRPCの両入口が共通業務コードを利用する |
| 5 | CLI残項目、計測、運用処理、配備先別の実行対応、全体結合テスト、文書 | 全受け入れ条件と第6節のシナリオを満たす |

全段階が必須であり、段階1・2だけを初版の完成とはしない。セキュリティと各機能のテストは該当段階で実装し、最終段階へ先送りしない。

## 8. 実装着手時に確定する事項

以下は機能の削除・延期を意味しない。公開APIを具体化する際に判断し、決定を本書へ反映する。

- Rustの最低対応バージョン、Tokioのバージョン・有効化する機能、HTTP・DBアクセスなどに採用するクレートとライセンス。
- gRPC基盤とProtobuf生成crate、handlerと検証の登録記法、streamingの範囲、gRPC statusへの変換、配備方法。HTTP/gRPCの同一プロジェクトでの併用と独立ビルドは確定方針とする。
- 第4.4節の契約を満たすmodelのderive・関連取得結果・query API、トランザクションの型と所有権の具体的な記法。
- 第4.6.1節の設計案に沿ったRequestのderive・ルール属性・Validated/Patch型・同期/非同期customの具体的な記法。
- 第4.2.1節のmiddleware関数・Next・認証登録ヘルパーの具体的な型と、採用HTTP基盤への接続方法。
- SQL migrationを標準とする案の採用クレート、非トランザクション実行・dirty履歴・repairの実装方法。
- OpenAPI生成と検証のクレート、ドキュメントUI、ルート・型のメタデータ記法。実行時の登録情報と生成用情報を共有する方法。
- 設定値の既定値一覧（実行スレッド数、各同時実行数・待機上限、各timeout、retry回数、token期限、サイズ上限、保存期間）。
- WebSocketのメッセージ形式、通知サイズ上限、クライアントの再接続手順。
- 配布方法、フレームワークと生成アプリのバージョン互換性。
- Dockerの実行用ベース、target名・バイナリ名、Lambda用adapterとワンショットタスクの呼び出し入口。HTTP/worker間の依存分離とイメージ別ビルドは確定方針とする。
- OTelの採用crate・バージョン、対応する環境変数、初期化の拡張口、`add otel`の対象選択と編集方法。通常ログにtracingを使い、SDK/exporterを任意依存にする方針とする。

これらが決まるまでは、CLI名`kouga`を除くサブコマンド構成・ディレクトリ配置を設計案として扱う。機能範囲と受け入れ条件は実装の基準とする。
